# Agent Engineering Loop

Agent Harness 的核心闭环应按 agent 运行时行为拆分，而不是按文档或工具模块拆分：

Orient -> Retrieve -> Plan -> Act -> Observe -> Evaluate -> Learn -> Govern。

中文表达为：

定向 -> 检索 -> 规划 -> 行动 -> 观察 -> 评估 -> 学习 -> 治理。

## Orient / 定向

让 agent 判断当前任务属于什么类型、应该进入哪条工作流、需要加载哪些基础约束。

它回答：

- 我现在在哪个任务类型里？
- 当前任务的主要风险是什么？
- 哪些项目边界必须先加载？
- 是否需要用户补充产品取舍？

## Retrieve / 检索

让 agent 找到相关上下文和已有实现，而不是凭空生成。

它回答：

- 有没有类似页面、组件、函数、类、service、hook、测试或设计实现？
- 相关调用链和影响面是什么？
- 设计稿、文档、ADR 或外部资料里有哪些必要事实？
- 哪些候选实现值得进一步阅读？

codebase-memory-mcp 适合承担代码结构、相似实现、调用链和影响面检索；Figma MCP 适合承担设计结构和视觉事实检索；Web/Docs MCP 适合承担外部事实检索。

## Plan / 规划

让 agent 在行动前形成可执行策略。

它回答：

- 应该复用、改造还是新增？
- 变更属于哪个层级或模块？
- 哪些依赖边界不能越过？
- 应该怎么分步执行？
- 完成后用什么证据验证？

复用判断不依赖人工维护的 TSDoc 索引，而依赖检索结果、真实使用样例、项目上下文和 skill 中的复用决策协议。

## Act / 行动

让 agent 调用工具并修改工程。

它包括：

- 编辑代码
- 调用 MCP
- 生成文件
- 运行命令
- 操作浏览器
- 读取 Figma
- 执行测试

行动必须受权限、边界和验证协议约束。

## Observe / 观察

让 agent 从真实环境读取行动后的反馈。

反馈可以来自：

- 编译输出
- lint 输出
- 测试输出
- 截图
- DOM
- console
- network
- logs
- visual diff
- MCP 返回结果

观察阶段让 agent 从猜测回到事实。

## Evaluate / 评估

让 agent 判断结果是否满足目标。如果不满足，先归因，再重试。

失败类型包括：

- 上下文不足
- 工具使用错误
- 设计理解错误
- 代码实现错误
- 测试或检查本身有问题
- 项目约束没有被显式记录

用可执行或可观察证据证明任务完成。

对 UI 任务，验证不应只停留在 TypeScript 或 lint，还应包含页面可访问性、视觉截图和关键布局检查。

## Learn / 学习

如果人工介入纠正了 agent，说明 harness 缺少信息。沉淀方式可以是：

- 更新 `docs/product/domain.md`
- 更新 `docs/architecture/`
- 新增 ADR
- 更新 skill
- 增加检查脚本
- 新增验证用例
- 记录到 issue 或 exec plan

核心问题是：这次学到的规则应该写回哪里，才能避免下次重复犯错。

## Govern / 治理

定期清理 agent 造成的重复、漂移和腐烂，包括重复组件、错误命名、无用文档、失效规则和过度复杂的索引。

治理阶段还应检查 MCP 可用性、skill 是否仍有效、检索协议是否被遵守、验证门是否能覆盖真实风险。
